# 프로젝트 전체 구상

> 계획서(정보과학 프로젝트) 내용을 바탕으로, 실제 구현 관점에서 정리한 문서.
> 진행하면서 계속 갱신한다.

## 1. 한 줄 정의

사용자가 관심 있는 선수·팀을 고르면 관련 이적설 기사를 모아 보여주되, 각 기사를 쓴
기자·매체가 얼마나 신뢰할 만한지 함께 표시해 주는 서비스.

## 2. 전체 아키텍처

```
1~5차시: Next.js 프론트만으로 완결된 서비스 (더미 데이터 배열 사용)
           ↓
6~8차시: Supabase(Postgres)를 붙여서 더미 데이터를 실제 DB 데이터로 교체
```

- **프레임워크**: Next.js (App Router) + TypeScript
  - 컴포넌트 단위로 화면을 쪼개서 만들기 쉽고, Vercel 배포가 매우 간단해서 5차시 목표(첫 배포)에 적합.
- **스타일**: Tailwind CSS — 클래스만으로 빠르게 UI를 만들 수 있어 매 차시 진도를 맞추기 좋음.
- **배포**: Vercel (5차시, 배포 완료).
- **DB**: Supabase — Postgres 기반, 테이블 설계가 계획서의 "저장할 데이터" 항목과
  1:1로 대응됨. 스키마는 [`supabase/schema.sql`](../supabase/schema.sql) 참고
  (6차시: 테이블 생성 + 클라이언트 연동. 아직 로그인 기능이 없어서 RLS는 꺼둔 상태 —
  자세한 이유는 schema.sql 상단 주석 참고).
- **상태 관리**: 별도 라이브러리 없이 React `useState` + props로 충분 (규모가 작음).

```
  auth.ts                  # useAdminSession() — 로그인 상태 구독 훅

  AdminGate.tsx             # /admin 하위 페이지를 감싸서 로그인 안 했으면 /admin/login으로

  admin/settings/page.tsx   # 클럽 이름·로고 URL 등을 직접 수정하는 화면
supabase/
  schema.sql에 RLS 정책 추가  # 테이블마다 select는 공개, insert/update/delete는 로그인 필요
```

> **진짜 보안은 RLS가 한다.** `/admin`에 로그인 화면을 붙이는 것만으로는 안전하지
> 않다 — anon key로 Supabase REST API를 직접 호출하면 로그인 화면을 그냥
> 우회할 수 있기 때문이다. 그래서 `supabase/schema.sql`에서 모든 테이블에
> RLS를 켜고, "select는 `using (true)`로 전체 공개, insert/update/delete는
> `auth.role() = 'authenticated'`만 허용" 정책을 걸었다. 로그인 UI는 그 위에
> 얹힌 편의 기능이다.
>
> 기사 등록·클럽 수정 모두 서버 API 라우트를 거치지 않고 **로그인된 브라우저가
> Supabase에 직접** 쓴다(`@supabase/supabase-js` 클라이언트가 로그인 세션을
> 자동으로 들고 다님). 예전엔 공개 폼이라 서버에서 점수를 재계산해 "입력값
> 조작 방지"를 했는데, 이제는 로그인한 관리자만 쓸 수 있어서 그 방어가
> 필요 없어졌다 — `lib/articleMutations.ts`가 클라이언트에서 바로 계산한다.

> **클럽 설정과 실제 배지 연동 (버그 수정).** `/admin/settings`를 처음 만들
> 때 clubs 테이블을 수정하는 화면만 만들고, 정작 메인 화면 배지
> (`TeamBadge`)는 여전히 `lib/teams.ts`에 박아둔 고정 목록만 보고 있어서
> 설정을 바꿔도 반영되지 않는 버그가 있었다. `fetchLiveData()`가 이제
> clubs 테이블도 같이 읽어오고, `TeamBadge`는 `clubs.logo_url`/`short_code`가
> 있으면 그걸 우선 쓰도록 고쳤다 — 설정 화면 저장이 실제로 화면에 반영된다.
> `supabase/backfill_club_logos.sql`은 기존에 고정 목록으로 떠 있던 로고들을
> clubs 테이블로 한 번 옮겨 채워주는 스크립트(1회 실행).
>
> 단, **클럽 "이름"을 바꾸는 건 과거에 등록된 기사에는 소급 적용되지 않는다**
> — `articles.from_team`/`to_team`은 clubs 테이블을 참조(FK)하는 게 아니라
> 그 시점에 입력된 텍스트를 그대로 저장해두는 구조이기 때문이다. 이름을
> 바꾸면 clubs 목록(앞으로 기사 등록할 때 자동완성 후보)만 바뀌고, 이미 저장된
> 기사의 팀 이름 표시는 그대로다. 로고 URL·약자는 팀 이름으로 매칭해서 그때
> 그때 조회하는 구조라 수정하면 바로 반영된다.

> **회원가입 + 기사 등록 권한 개방 (8차시 이후 추가).** 처음엔 관리자 계정
> 1개만 Supabase 대시보드에서 수동으로 만들어서 그 사람만 기사를 등록할 수
> 있었는데, 이제 `/signup`으로 누구나 가입해서 로그인만 하면 기사를 등록할
> 수 있게 열었다. 대신 클럽 설정(팀 엠블럼 등 수정)은 여전히 관리자만 써야
> 해서, "이 사람이 관리자인가"를 구분하는 `profiles` 테이블(`is_admin`
> 컬럼)을 새로 만들었다 — 가입할 때 DB 트리거(`handle_new_user`)가 자동으로
> `is_admin = false`인 행을 복사해두고, 관리자로 승격하려면 SQL Editor에서
> `update profiles set is_admin = true where email = '...'`를 직접 실행해야
> 한다(앱 화면에서 셀프 승격은 못 하게 의도적으로 막음).
>
> 화면 쪽은 게이트(gate) 컴포넌트를 두 개로 나눴다:
> - `AuthGate` — 로그인만 확인 (`/admin` 기사 등록 화면)
> - `AdminGate` — 로그인 + `profiles.is_admin`까지 확인 (`/admin/settings`)
>
> RLS 정책도 테이블마다 다르게: `articles`는 "쓰기는 로그인한 사용자 누구나"
> 그대로 두고, `clubs`만 "쓰기는 `profiles.is_admin = true`인 사용자만"으로
> 바꿨다.

> **새 선수·새 클럽 등록 (8차시 이후 추가).** 기사 등록 폼이 "이미 있는
> 선수·팀만" 다룰 수 있었던 공백을 메웠다.
> - **선수**: `players` 테이블에 없는 선수는 등록 자체가 막혀 있었다
>   (`PlayerSearchSelect`가 검색만 지원, 자유 입력 불가). 이제 검색 결과가
>   없으면 그 자리에서 현재 소속팀만 같이 입력해 바로 새 선수로 추가하고
>   이어서 선택할 수 있다. `players` 쓰기는 원래도 "로그인한 사용자 누구나"
>   정책이라 관리자가 아니어도 된다.
> - **클럽**: "이적 전/후 팀" 입력란은 원래도 자유 텍스트라 새 팀 이름을
>   타이핑하면 기사 저장은 됐지만, `clubs` 테이블엔 안 들어가서 로고도 없고
>   `/admin/settings`에도 안 보였다. 이제 `lib/articleMutations.ts`의
>   `ensureClubExists()`가 기사 저장 시 `from_team`/`to_team`을 `clubs`에
>   `ON CONFLICT (name) DO NOTHING`으로 upsert해둔다 — 이미 있으면 그냥
>   건너뛰고, 처음 보는 팀이면 로고 없는 기본값으로 행을 만들어서 나중에
>   관리자가 `/admin/settings`에서 로고·약자를 채울 수 있게 한다. 이를 위해
>   `clubs`의 쓰기 정책도 세분화했다: **추가(insert)는 로그인한 사용자
>   누구나**(새 클럽 메타데이터를 만드는 건 위험이 낮음), **수정·삭제는
>   여전히 관리자만**(기존 클럽의 이름·로고를 함부로 바꾸거나 지우지 못하게).

> **부가 기능 일괄 추가 (8차시 이후).** 수업 과제 요구사항인 "부가 기능
> 3개 이상"을 충족하기 위해 한 번에 여러 기능을 추가했다.
>
> - **기자 신뢰도 랭킹** (`/journalists`) — 기자별 평균 개별 신뢰 점수·기사
>   수 집계. 새 테이블 없이 기존 articles/journalists만으로 계산.
> - **마이페이지** (`/mypage`) — 내가 등록한 기사만 모아보고 수정(링크·
>   확실성·요약·날짜)·삭제 가능. 이를 위해 `articles.created_by`(작성자
>   uuid)와 `articles.created_at`(실제 등록 시각, published_at과는 다름)을
>   새로 추가하고, `articles` RLS를 "등록은 누구나, 수정/삭제는 본인 글이거나
>   관리자만"으로 나눴다(`insert_authenticated` / `update_own_or_admin` /
>   `delete_own_or_admin` 정책).
> - **즐겨찾기** — `favorites(user_id, player_name)` 테이블. 하트 버튼으로
>   토글, 전체 집계가 공개라 "즐겨찾기순" 정렬에도 쓴다.
> - **조회수** — `rumor_views(player_name, view_count)` 테이블 + 보안
>   definer 함수 `increment_rumor_view()`. 테이블 자체엔 쓰기 정책을 안 둬서
>   REST API로 숫자를 직접 조작 못 하게 막고, 오직 이 함수를 통해서만
>   +1 할 수 있다. 상세 페이지 방문마다 호출.
> - **정렬** — 메인 화면에 최신순/즐겨찾기순/조회수순 토글 추가
>   (`lib/filters.ts`의 `sortRumors`).
> - **댓글** — `comments(player_name, user_id, email, body)` 테이블. 상세
>   페이지 하단에 목록 + 작성 폼. 로그인한 사용자만 작성, 본인 글이거나
>   관리자만 삭제 가능.
> - **기사 신뢰도 투표(동의/반대)** — `article_votes(article_id, user_id, vote)`
>   테이블. 기자·매체가 매긴 점수와는 별개로 실제 방문자 의견을 모으는
>   기능. 유저당 기사당 투표 1개(의견 바꾸면 upsert).
> - **공유 기능** — 상세 페이지에 `generateMetadata`로 OG 메타태그(카카오톡/
>   트위터 공유 시 미리보기)를 달고, "공유하기" 버튼은 Web Share API가
>   있으면 그걸, 없으면 링크 복사로 대체.
> - **최근 등록 하이라이트** — 등록된 지 24시간 안이면 카드에 "NEW" 배지.
>   `published_at`(사용자 입력 날짜)이 아니라 실제 DB `created_at` 기준.
> - **다크 모드** — Tailwind v4 `@custom-variant dark`로 클래스 기반 전환을
>   추가하고, 헤더의 토글 버튼이 `<html>`에 `dark` 클래스를 붙였다 떼었다
>   한다. 선택은 `localStorage`에 저장, 없으면 시스템 설정을 따른다.
>
> `fetchLiveData()`는 이제 `clubs`/`favorites`/`rumor_views`까지 한 번에
> 읽어오고, `React.cache()`로 감싸서 같은 요청 안에서 중복 조회(상세
> 페이지의 `generateMetadata` + 페이지 본문이 둘 다 부르는 경우)를 막는다.

## 3. 데이터 모델 (계획서 2번 항목 기준)

3개 테이블. 3~5차시는 이 구조를 그대로 TypeScript 타입 + 더미 배열로 먼저 만들고,
6차시에 Supabase 테이블로 옮긴다.

### `journalists` (기자)

| 필드 | 설명 |
|---|---|
| id | PK |
| name | 기자 이름 |
| outlet | 소속 매체 |
| league_tiers | `{ league: string, score: number }[]` — 리그별 신뢰도 티어 점수 |
| base_tier | 기본 신뢰도 티어 점수 (담당 리그 기록이 없을 때 대신 사용) |

### `articles` (기사)

| 필드 | 설명 |
|---|---|
| id | PK |
| url | 원문 링크 |
| journalist_id | FK → journalists |
| player_name | 관련 선수명 |
| from_team / to_team | 이적 전 / 이적 후 팀 |
| certainty | 확실성 카테고리: `확정` \| `진전` \| `관심` |
| summary | 요약 코멘트 |
| published_at | 등록 날짜 |
| score | 계산된 개별 신뢰 점수 (파생값) |

### `rumors` (이적설)

| 필드 | 설명 |
|---|---|
| id | PK |
| player_name | 관련 선수명 |
| article_ids | 관련 기사 id 목록 |
| aggregate_score | 종합 신뢰 점수 (파생값) |
| updated_at | 최종 업데이트 날짜 |

### `players` (선수) — 계획서 원안엔 없던 4번째 테이블, 7차시 진행 중 추가

관리자 등록 폼에서 "선수를 검색해서 선택"하고, 선택하면 현재 소속팀으로
"이적 전 팀"을 자동으로 채우기 위해 추가했다. `articles.player_name`은 여전히
단순 텍스트 컬럼이라(관계형으로 바꾸지 않음) 이 테이블과 FK로 묶여있지 않다 —
순수하게 등록 폼의 입력 보조용.

| 필드 | 설명 |
|---|---|
| id | PK |
| name | 선수 이름 (unique) |
| current_team | 현재 소속팀 |

> 지금은 공식 10명만 들어있지만(`supabase/seed.sql`), 실제 배포할 때는 여기에
> 선수를 더 많이 추가하면 등록 폼의 검색-선택에 그대로 반영된다.

## 4. 신뢰도 계산 로직 (계획서 2번 "처리" 항목 기준)

1. 기사 등록 시 선수/팀/기자/날짜 기준으로 태그 부여.
2. `(기자, 기사에 태그된 리그)` 조합으로 `journalists.league_tiers`에서 티어 점수 조회.
   - 해당 리그 기록이 없으면 `base_tier` 사용.
3. `개별 기사 신뢰 점수 = 티어 점수 × 확실성 가중치`
   - 확실성 가중치(초기안, 조정 예정): `확정 = 1.0`, `진전 = 0.7`, `관심 = 0.4`
4. `종합 신뢰 점수 = 같은 이적설에 속한 기사들의 개별 점수 평균`
   - 1단계: 단순 평균으로 구현 (5차시 목표)
   - 2단계 개선: 최신 기사에 가중치를 더 주는 방식으로 발전 (계획서 5번 "대비 방법"과 동일)

이 계산 함수는 `lib/trustScore.ts`에 순수 함수로 작성해서, 더미 데이터든 실제 DB
데이터든 동일하게 재사용한다 (3~5차시는 더미 배열을 넣고, 8차시에 실제 DB 조회
결과를 넣기만 하면 되도록).

> **리그 태그 규칙**: 2번의 리그 태그는 "이적 전 소속팀(from_team)의 리그"를 기준으로
> 정한다. 예) AC 밀란(세리에 A) 선수가 첼시(프리미어리그)로 이적하는 기사는
> `league: 세리에 A`. 이렇게 해야 디 마르치오(세리에 A 전문)·플레텐베르크(분데스리가
> 전문) 같은 리그 특화 기자가 실제로 자기 전문 리그에서 높은 점수를 받는 사례와,
> 전문 리그가 아닐 때 기본 티어로 대체되는 사례를 둘 다 보여줄 수 있다.

## 5. 화면 구성

계획서 3번 스케치 기준, 핵심 화면 3개:

1. **메인 화면**: 검색창 + 왼쪽 사이드바(팀별/기자별/선수별 필터) + 이적설 카드 목록.
   - "최신순"은 항상 적용되는 기본 정렬이고, "팀별/기자별/선수별"은 사이드바에서
     구체적인 팀·기자·선수를 선택해 목록을 실제로 걸러내는 필터다(가나다순 재배열이 아님).
2. **상세 화면**: 특정 이적설의 관련 기사를 날짜순 타임라인으로 표시 (기자/매체/확실성/개별 점수/원문 링크).
3. **관리자 기사 등록 화면**: 기사 링크·기자 이름·관련 선수·관련 팀·확실도 입력 폼.

### 5-1. 카드 디자인 방향

- **왼쪽 사이드바 필터**: 상단 가로 버튼 대신 세로 사이드바에 "팀별/기자별/선수별"
  섹션을 두고, 각 섹션 안에 실제 선택지(팀 이름·기자 이름·선수 이름) 버튼을 나열한다.
  나중에 필터 종류가 늘어나도(리그 추가, 이적료 범위 등) 섹션만 추가하면 되는 구조.
- **출처 표기**: 카드 하단에 "1주 전 · 데이비드 오른스타인 ↗"처럼 상대 날짜 + 기자명 +
  링크 아이콘을 한 줄로 표시. 계획서의 "원문 링크" 요구사항과 그대로 대응된다.
- **팀 배지**: 실제 구단 로고 이미지 대신, 저작권 문제 없는 원형 이니셜 배지(TOT/MCI/MUN/LIV/CHE)로 스캔하기 쉽게 만든다.
- **화이트 배경 + 미니멀 타이포**: 색은 팀 배지에만 쓰고 나머지는 절제된 톤 유지.

## 7. 다룰 선수·팀 목록 (1차시 결과물)

더미 데이터(3차시)와 이후 화면 예시 전반에서 재사용할 기본 목록. 여러 리그를
넓게 다루는 대신 **프리미어리그, 그 중에서도 토트넘 관련 이적설**에 집중해서
범위를 좁혔다.

**팀 (5, 우선순위 순 — 토트넘이 최우선)**

1. 토트넘 홋스퍼
2. 맨체스터 시티
3. 맨체스터 유나이티드
4. 리버풀
5. 첼시

**선수 (5, 공식 목록)**

1. 오마르 마르무시 — 맨시티 → 토트넘
2. 사비뉴 — 맨시티 → 토트넘
3. 미하일로 무드릭 — 첼시 → 토트넘 (임대)
4. 루카 부슈코비치 — 브라이튼 → 토트넘
5. 코디 가크포 — 리버풀, 토트넘/맨시티가 영입 경쟁하는 구도

> **더미 데이터 확장 (3차시)**: 필터(팀별/기자별/선수별)를 제대로 테스트하려면
> 카드가 훨씬 많아야 해서, 위 5명 외에 5팀이 골고루 걸리도록 5건을 더 추가했다
> (`lib/dummyData.ts` 기준, 총 10건·25개 기사). 5개 핵심 팀은 그대로 유지하면서
> 상대 구단만 다양화(PSG·도르트문트·AC밀란·레알 마드리드·알-힐랄 등)했다.
>
> 6. 곤살로 라모스 — PSG → 맨체스터 유나이티드
> 7. 니코 슐로터베크 — 보루시아 도르트문트 → 리버풀
> 8. 라파엘 레앙 — AC 밀란 → 첼시
> 9. 브루누 페르난데스 — 맨체스터 유나이티드 → 알-힐랄 (아웃고잉)
> 10. 콜 파머 — 첼시 → 레알 마드리드 (아웃고잉)
>
> ⚠️ 위 10명·관련 이적설은 `lib/dummyData.ts`에만 있는 **더미(가상) 데이터**다.
> 8차시부터 화면은 더미 데이터를 안 쓰고 실제 Supabase DB만 보기 때문에,
> 지금은 화면에 안 뜬다 — 코드 참고용으로만 남아있다.

> **실제 데이터 확장 (7~8차시 이후, `supabase/seed.sql` / `seed_real_articles.sql`)**:
> `players` 테이블에 공식 10명 외에 실제로 존재하는 유명 선수 45명을 더
> 추가했고(현재 소속팀 포함), `clubs` 테이블에 유럽 5대 리그 전체 96개 구단을
> 넣었다. `articles`에는 실제로 있었던(완료된) 이적 사례 6건을 각각 3개 기사로
> — 벨링엄(도르트문트→레알 마드리드), 라이스(웨스트햄→아스널), 엔소
> 페르난데스(벤피카→첼시), 음바페(PSG→레알 마드리드), 비르츠(레버쿠젠→
> 리버풀), 파머(맨시티→첼시) — 추가했다. 사실관계는 실제 보도 기준으로
> 정확하게 맞췄고, 원문 링크는 특정 기사 URL 대신 각 기자의 실제 공개
> 프로필/매체 홈페이지로 연결해뒀다.

> **친구 피드백 반영: 엠블럼 버그 + 이적설 결과 표시 (8차시 이후).**
>
> - **엠블럼 버그 수정**: 레버쿠젠·벤피카가 실제 엠블럼 대신 회색 이니셜
>   배지로 보인다는 피드백. 원인은 둘 다 로고 URL이 한 번도 채워진 적이
>   없었던 것(레버쿠젠은 `supabase/backfill_club_logos.sql`이 커버한 17개
>   팀에 없었고, 벤피카는 5대 리그 96개 클럽 목록 자체에 없었음 — 포르투갈
>   리그는 범위 밖). `supabase/fix_club_logos_leverkusen_benfica.sql`로
>   둘 다 로고를 채우고, 레버쿠젠·레반테가 둘 다 short_code `LEV`를 쓰던
>   충돌도 레버쿠젠을 `B04`로 바꿔서 해소했다. 96개 중 실제 로고가 있는
>   건 여전히 17개(+레버쿠젠)뿐 — 나머지는 전부 같은 "로고 없음, 이니셜만"
>   상태라, 필요하면 추가로 채우는 작업을 별도로 진행해야 한다.
> - **이적설 결과(진행중/성사/무산)**: `rumors` 테이블(그동안 안 쓰던
>   테이블)에 `status`/`actual_team`/`resolved_at` 컬럼을 추가해서, 선수별로
>   "예측 신뢰 점수"와 "실제 결과"를 같이 보여준다. 행이 없는 선수는 기본값
>   그대로 "진행중" 취급(앱 코드에서 처리) — 그래서 더미/미확정 이적설은
>   손댈 필요가 없다. 마이그레이션은 `supabase/migration_rumor_outcome.sql`.
>   웹 검색으로 재확인한 실제 공식 발표일 기준으로 6건(벨링엄/라이스/엔소/
>   음바페/비르츠/파머) 모두 "성사"로 채웠다 — 전부 실제로 일어난 이적이라
>   "무산" 사례는 아직 없다. 상세 페이지에 "종합 신뢰 점수 N점 → 실제 결과:
>   …" 한 줄로 나란히 보여주고, 메인 카드에도 작은 상태 뱃지를 붙였다.
>   종결된(성사/무산) 이적설은 기사 동의/반대 투표 버튼이 비활성화된다 —
>   결과가 나온 뒤에는 투표가 의미 없어서.

> **기자 신뢰도 보정 (8차시 이후).** 결과가 확정된 이적설을 바탕으로 기자의
> 신뢰도를 실제 적중/빗나감 기록으로 보정한다.
> - **판정**: 결과 확정 이적설의 확정/진전 기사만 판정한다. 무산이면 그
>   기사가 말한 도착팀이 뭐든 빗나감, 성사면 그 기사의 도착팀이 실제
>   도착팀과 같을 때만 적중. **관심 단계 기사는 판정에서 제외**한다 —
>   확정적 주장이 아니라서 맞다/틀리다를 매기기 적합하지 않고, 판정
>   기사가 0건인 기자는 수식상 자동으로 보정 전과 똑같이 유지된다는 깔끔한
>   성질도 생긴다. (`lib/trustScore.ts`의 `judgeArticle`)
> - **보정 공식**: 베이지안 평균(라플라스 스무딩). `보정비율 = (적중 수 + k ×
>   초기비율) / (판정 기사 수 + k)`, k=3. 초기비율은 기자의 `baseTier/100`
>   (리그별 티어 대신 전체를 통틀어 하나의 숫자로 — 표본이 원래도 적어서
>   리그별로 쪼개면 더 적어짐). 판정 기사가 0건이면 보정비율이 초기비율과
>   정확히 같아서 변화가 없다. (`calibrateJournalist`)
> - **기사 점수에 연결**: `calculateArticleScore`(저장 시점, DB의
>   articles.score)는 그대로 둔다 — "그 당시 알던 값"의 역사적 기록. 대신
>   `보정배율 = 보정비율 ÷ 초기비율`을 만들어서, 조회할 때마다
>   `articles.score × 보정배율`로 "화면에 보여줄 최종 점수"
>   (`calibratedScore`)를 다시 계산한다(0~100 clamp). 이적설의 종합 점수도
>   이제 원점수 평균이 아니라 이 보정된 점수의 평균이다 — 그래서 다른
>   이적설의 결과가 새로 확정될 때마다 이미 있던 이적설의 점수도 바뀔 수
>   있다. (`lib/supabaseData.ts`의 `enrichArticles`)
> - **기자 프로필 페이지** (`/journalist/[id]`): 소속·초기 티어·보정된
>   신뢰도(%)·판정 건수·적중 건수·쓴 기사 목록(기사별 적중/빗나감/진행중
>   표시)을 보여준다. 기사 카드·상세 페이지의 기자 이름에서 링크된다.
> - **점수 계산 근거 분해**: 상세 페이지 기사마다 "티어 N점(리그) × 확실성
>   가중치(문구) × 보정 배율(적중 M/판정 N) = 최종 점수"를 숫자로 보여준다.
> - **교차 확인(서로 다른 매체 수)은 표시만**: 이적설 상세 페이지에 "N명의
>   기자가 보도" 안내를 붙였지만, 점수 계산에는 아직 안 넣었다 — 매체 수를
>   그대로 점수에 더하면 "질 낮은 매체 여럿"이 "믿을만한 매체 하나"를
>   수치상 이길 수 있어서, 이 앱의 핵심 취지(신뢰도 가중, 인기 아님)와
>   충돌할 위험이 있다고 판단했다. 필요하면 나중에 별도로 추가.
> - 표본이 작아서 생기는 주의점: 예를 들어 던컨 카슬스(의도적으로 낮은
>   티어의 "대조군")가 실제 데이터에서 2건 중 2건을 다 맞혀서 보정 배율이
>   ×1.93까지 뛰었다 — k=3이 완전히 막아주진 못하는, 적은 표본에서 흔히
>   생기는 현상이다. 기사·이적설이 더 쌓이면 자연히 안정된다.

> 성사라서 적중률 계산에 "빗나감" 사례가 하나도 없었던 공백을 메웠다.

## 9. 보안 한계 (2번/3번 작업 기준)

> 2번(관리자 비밀번호)·3번(기사 승인) 작업을 하면서 확인한, **아직 해결
> 안 하고 제안만 해두는** 한계 두 가지. RLS를 켜거나 기존 정책을 바꾸는
> 변경은 사용자가 직접 확인하기 전에는 하지 않기로 했다(예전에 RLS가
> 켜져서 데이터가 안 보인 적이 있어서 신중하게 접근).
>
> **(1) 승인 대기/반려된 기사도 anon key로 직접 조회하면 보인다.**
> `articles` 테이블의 select 정책이 `using (true)`(전체 공개)라서,
> `approval_status`로 걸러주는 건 앱 코드(`fetchApprovedArticles()`)뿐이다.
> 우리 화면에서는 안 보이지만, 누구든 Supabase REST API를
> (`/rest/v1/articles?select=*`) anon key로 직접 호출하면 대기 · 반려
> 기사까지 전부 그대로 조회된다. 반려된 기사가 허위 · 부적절해서
> 숨기고 싶은 경우에도 원문 내용 자체는 API 레벨에서 계속 노출된다는
> 뜻. **제안(적용 안 함)**: `select_all` 정책을 `using (approval_status
> = '승인' or created_by = auth.uid())`로 좁히면(마이페이지에서 본인
> 글은 계속 보이게) 해결된다 — 다만 이건 기존 정책을 바꾸는 일이라
> 사용자 확인 후에 진행.
>
> **(2) anon key 자체로는 articles에 못 쓴다 — 이 부분은 그대로 안전.**
> `insert_authenticated`(로그인 필요) · `update_own_or_admin` 정책이
> 그대로 살아 있어서, anon key만 갖고 있고 로그인을 안 한 요청은 기사
> 등록 · 수정 · 승인/반려 전부 거부된다. 이번에 추가한 관리자 비밀번호
> 경로(승인/반려, 클럽 설정)는 RLS를 우회하는 service role key를 쓰지만,
> 그 키는 서버 Server Action 코드 안에만 있고 브라우저로 내려가지 않는다
> (비밀번호 쿠키를 모르면 그 Server Action 자체를 호출해도
> `requireAdmin()`에서 막힌다).
>
> **(3) 관리자 비밀번호 쿠키는 "공유 비밀" 방식이라, 비밀번호 유출 시
> 그대로 위조 가능.** 쿠키 값은 `ADMIN_PASSWORD`의 해시값이라 비밀번호를
> 알면 서버 왕복 없이도 같은 토큰을 계산해 쿠키를 직접 만들 수 있다.
